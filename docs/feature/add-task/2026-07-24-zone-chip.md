# Add task — an editable zone chip

Date: 2026-07-24
Covers: `:core:domain` task writer + attribute use case, `:core:design-system` dropdown menu item,
`:feature:add-task` chip row + ViewModel.

Follows `2026-07-23-length-menu-and-chip-in-design-system.md`. That plan stands; this one adds a
fourth editable chip.

## Why

The when and length attributes were pickable from their chips, but zone could only be set by typing
`@play` into the sentence. A zone chip existed, but it appeared only once a token was already typed —
so the one attribute with a fixed, short list of valid values (the day's zones) was the one you
couldn't pick from a list. This adds the missing chip, built exactly like the length one: an
always-present chip with a menu hanging off it.

## 1 — The chip is always present

`ZoneChip` no longer returns early when there is no token. It has four states:

- resolved → the zone's name, lavender, active
- resolving → "Finding zone…", lavender, inactive (a day change is refetching)
- an unresolved token → `Zone "x" not found`, destructive tone — a typo the user can see and fix
- nothing typed → "No zone", lavender, inactive — the same default-standing-in-for-a-value read as
  "Today" and "Any length"

`PoppingChip` (the enter/exit spring that wrapped the old conditional chip) is gone with its only
caller.

## 2 — Picking writes `@zone` back into the sentence

Same contract as every other chip: the choice is folded into the typed text, then re-parsed.

- `TaskAttribute.In(zoneName)` → `TaskInputWriter.withZone`, which replaces the existing `ZONE` token
  or appends `@name`.
- `AddTaskPicker.ZONE` drives an `AwanDropdownMenu` of the day's zones; each row writes the zone name.

The round-trip has one sharp edge. The parser's `@([\p{L}\p{N}_-]+)` token cannot hold a space, so a
multi-word zone can't be written verbatim. `withZone` writes the **first word** only (`@Deep` for
"Deep Work"); the four single-word defaults (Study/Work/Play/Personal) are therefore exact, and
[TaskInputParser] resolves the rest by `startsWith`. Marked with a `ponytail:` comment naming the
upgrade path (quoting: `@"Deep Work"` on both sides). This is not worse than the old typed flow — it
had the same limit — and the defaults are the only zones that ship today.

## 3 — The menu needs the day's zones loaded

The old `resolveZone` fetched only when a token was present, and only to resolve that token. The menu
needs the whole set regardless, so it became `refreshZones(token, date)`:

- fetches the day's zones only when the effective day changes (guarded on `loadedZoneDate`), reusing
  the cached set on every other keystroke — so preloading for the menu did not turn every keystroke
  into a fetch
- one fetch produces both `availableZones` (the menu) and `resolvedZone` (the token match)
- runs once at construction (`init`) so the menu is populated before anything is typed

## 4 — Empty-menu guard

A zone chip that opens an empty menu reads as broken — and it is reachable: a user who hasn't set up
zones (and, as it happens, the current dev backend, which seeds none) has an empty set. The menu
shows a single disabled "No zones set up yet" row in that case. `AwanDropdownMenuItem` gained an
`enabled` flag for it (muted ink, non-interactive) — a generally useful menu concern, not an
add-task one, so it lives in the design system.

## Tests

- Writer: `withZone` appends then replaces; single-word zones round-trip through the parser; a
  multi-word zone is written by its first word.
- ViewModel: picking a zone writes `@Play` and resolves it against the day's zones; `availableZones`
  is populated before any token is typed.

## Implementation notes (what actually differed)

Verified with `./gradlew :core:domain:testDebugUnitTest :feature:add-task:testDebugUnitTest` (green),
`:app:installDebug`, and by driving the sheet on emulator-5554.

**The dev backend seeds no zones**, so on-device only the empty path could be exercised end to end:
typed `Gym tomorrow 6pm @play` → chip read `Zone "play" not found` (correct unresolved state), and
tapping the "No zone" chip opened the menu onto "No zones set up yet". The populated path — menu of
zones, tap writes `@Play`, chip resolves to the zone — is covered by the ViewModel/writer tests, not
a screenshot. Worth re-checking on a build with real zones.

**First on-device attempt to record the empty menu missed:** tapping `+` and then the chip position
in one go landed the second tap on the Goals nav item because the sheet had not finished animating
in. Not a code issue — the sheet needs a beat before its chips are hittable.

### Deviation

- `withZone`'s first-word-only write is the one place a picked value does not round-trip byte-for-byte
  through the parser. Documented in code; acceptable because every shipping zone is single-word.
